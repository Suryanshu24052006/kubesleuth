Root causes, with receipts.

kubesleuth is an AI agent that investigates Kubernetes incidents the way an on-call engineer does. It weighs competing explanations, checks every claim word for word against the cluster's own data, and names a root cause only when independent sources agree.

    What it does, and why it helps on a normal day

    When an alert fires, kubesleuth reads the alert, looks at what changed recently, writes down competing explanations, and then queries pods, metrics, logs, traces and change history until one cause is clearly ahead and backed by independent sources. It ends with a root-cause report: the cause, the quoted evidence, a timeline, what it ruled out, and what is still uncertain. It never changes the cluster; a person makes the fix.

    Faster on-call

    The first minutes of an incident usually go to opening dashboards, tailing logs and asking whether anyone deployed. kubesleuth does that sweep and hands the on-call engineer a drafted RCA, so they start from a lead instead of a blank screen.

    What changed, and who changed it

    Most incidents follow a change. The change journal answers that in one line, with the diff, the person or tool behind it, and whether it is still in effect.

    Cause, not noise

    One bad change can trip alerts across several services. Telling the service that fails apart from the change that broke it is where people lose the most time.

    Safe to run in production

    It can only read, only one namespace, with no credentials of its own, secrets redacted and every query logged. Nobody has to worry about it "fixing" things.

    Honest when unsure

    It says "inconclusive" and lists what it couldn't check, rather than giving a confident wrong answer that sends the team down the wrong path.

    Post-mortems and teaching

    Every report has the same structure and quoted evidence: a solid first draft for the write-up, and a step-by-step record juniors can learn from.

    Six real outages, three live runs

    Each run builds a fresh cluster on a GitHub-hosted machine, breaks it the way a published post-mortem describes, waits for the alert, and lets two reasoners investigate the same incident: a rule-based baseline and the LLM agent (Gemini, free tier). An answer counts as correct only if it names the right component and the actual mechanism.

    The baseline wins on single changes

    When one recent change explains everything, simple rules are fast and reliable: 9 of 9 on the S3, EBS and Knight Capital outages.

    The LLM wins on reasoning

    When the cause has to be worked out across sources, such as an amplifying health check or one bad regex rule, only the LLM gets there: 3 of 3 on Chef, 2 of 3 on Cloudflare.

    How it works

    Two processes that never share credentials. The agent talks to the language model but cannot touch the cluster. A small read-only broker is the only way in, and it can only read one namespace.

    No made-up evidence

    Every piece of evidence must quote a tool's output word for word. Code checks the quote exists; if it doesn't, the claim is thrown out and shown as rejected.

    Confidence from evidence, not from the model

    The model grades evidence; code turns it into probabilities. High confidence needs at least two independent sources and nothing strongly against it.

    Symptoms are never the answer

    Error spikes, restarts and failed probes are tracked as things that need explaining, and the agent is not allowed to report one as the root cause.

    It knows what changed, and who changed it

    The broker records field-level diffs, the person or tool behind each one, and whether the change is still in effect: DB_POOL_SIZE 4 → 30, by kubectl.

    The outages it investigates

    Each scenario recreates the mechanism of a published post-mortem, including the part that made it hard to diagnose. A pod that keeps logging prompt-injection messages runs in every scenario.

      Safe even if the model is fooled

      The agent has no cluster credentials, can only reach the broker, and the broker has no tool that writes, deletes, runs commands or reads secrets. These checks passed on the live cluster in all three runs.

        What running it for real taught me

        The live runs found nine problems that tests on recorded data never showed. Each one is fixed and guarded by a test.

        1. Live tool results are far bigger than test data; a trimming marker crashed the agent's timeline.
        2. Port-forward tunnels died silently, so early evaluations never reached the cluster.
        3. A retired model kept the run going and produced a misleading "inconclusive" instead of an error.
        4. Free-tier limits forced a redesign to one model call per round, with retries and model fallback.
        5. Models returned near-miss JSON; parsing now normalises it while evidence still has to pass the quote check.
        6. A broker bug credited kubectl scale to the Kubernetes controller instead of the person.
        7. Changes already reverted by an earlier scenario misled the baseline; changes now say if they are still in effect.
        8. The small test machine got so loaded that containerd refused connections; resets now restart only what changed.
        9. My first scorer was too lenient and credited an answer that blamed a victim; all runs were re-graded strictly.
